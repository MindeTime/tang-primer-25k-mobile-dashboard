۱. آشنایی با Hermes

Hermes Agent یک عامل هوش مصنوعی قابل اجرا در محیط خط فرمان است. برخلاف یک گفت‌وگوی ساده، می‌تواند با ابزارهای مجاز کار کند، فایل‌ها را بررسی کند، فرمان اجرا کند و نتیجه یک مأموریت چندمرحله‌ای را به شکل گزارش تحویل دهد.

کاربرد اصلی در این پروژهسپردن بررسی‌های فنی مستقل به Hermes؛ مانند ممیزی کد LiteX، تحلیل گزارش سنتز، بررسی پین‌ها، ارزیابی محدودیت‌های منابع و تهیه گزارش قابل بازبینی.

Hermes یک کمک‌تحلیل‌گر است، نه مرجع نهایی تأیید سخت‌افزار. هر نتیجه مهم باید با شواهد، فایل خروجی و در صورت لزوم بررسی مستقل تأیید شود.

توجهاین‌ها مقادیر ثبت‌شده از تنظیمات قبلی هستند و لزوماً وضعیت لحظه‌ای سیستم را نشان نمی‌دهند. قبل از هر تغییر، تنظیمات واقعی را فقط‌خواندنی بررسی کنید. کلید API یا رمزها را در گزارش، اسکرین‌شات یا مخزن GitHub قرار ندهید.

۳. شروع و بررسی سلامت

فرمان‌های پایه را در ترمینال اجرا کنید. این فرمان‌ها برای مشاهده وضعیت‌اند و نباید پروژه FPGA را تغییر دهند.

hermes --help
hermes doctor
hermes model
hermes tools
  • hermes --help: نمایش فرمان‌ها و گزینه‌های موجود در نسخه نصب‌شده.
  • hermes doctor: بررسی سلامت نصب و وابستگی‌ها.
  • hermes model: مشاهده یا پیکربندی ارائه‌دهنده و مدل؛ بدون شناخت تنظیمات فعلی، گزینه‌ها را تغییر ندهید.
  • hermes tools: بررسی ابزارهای فعال و مجوزهای آن‌ها.

برای شروع گفت‌وگو، فرمان hermes را اجرا کنید. برای جزئیات فرمان‌های نسخه جاری، خروجی hermes --help و مستندات رسمی را ملاک قرار دهید؛ نام گزینه‌ها ممکن است با نسخه‌ها تغییر کند.

۴. مدل و اتصال API

Hermes برای پاسخ‌گویی به یک provider و مدل نیاز دارد. در تنظیمات فعلی پروژه، یک endpoint سازگار با API و نام مدل اختصاصی ثبت شده است.

چک‌لیست اتصال

  1. آدرس endpoint باید شامل مسیر پایه درست باشد؛ برای تنظیم فعلی مقدار ثبت‌شده /v1 است.
  2. نام مدل باید دقیقاً با نامی که سرویس‌دهنده ارائه می‌کند مطابقت داشته باشد.
  3. کلید API باید در محل امن تنظیمات محلی قرار گیرد؛ آن را در متن مأموریت وارد نکنید.
  4. ابتدا یک پیام کوتاه آزمایشی بفرستید و پاسخ را بررسی کنید.
  5. اگر خطا رخ داد، زمان، متن خطا و کد HTTP را بدون افشای کلید ثبت کنید.
این صفحه عمداً فرمانی برای بازنویسی فایل پیکربندی یا تعویض provider ارائه نمی‌کند. ابتدا از تنظیمات موجود نسخه پشتیبان بگیرید و فقط با اجازه صریح، تنظیمات را تغییر دهید.

۵. گردش‌کار استاندارد برای هر مأموریت

  1. تعریف هدف: دقیقاً مشخص کنید چه چیزی باید بررسی شود و خروجی مورد انتظار چیست.
  2. تعیین محدوده: مسیر پروژه، فایل‌های مجاز و فایل‌های ممنوع را مشخص کنید.
  3. حالت فقط‌خواندنی: ابتدا ساختار و شواهد را جمع‌آوری کند؛ هیچ تغییری ندهد.
  4. تحلیل: فرضیه‌ها، وابستگی‌ها، محدودیت‌ها و موارد نامطمئن را بررسی کند.
  5. آزمایش مستقل: اگر لازم است، آزمایش را در پوشه جدید و جداگانه انجام دهد.
  6. گزارش: نتیجه، شواهد، فرمان‌ها، فایل‌های تولیدشده و محدودیت‌ها را تحویل دهد.
  7. بازبینی: شما گزارش را بررسی کنید؛ هرگونه تغییر یا پروگرام سخت‌افزار نیازمند اجازه جداگانه است.

۶. چطور مأموریت دقیق بنویسیم؟

یک مأموریت خوب باید هدف، محدوده، محدودیت، روش و قالب تحویل را روشن کند.

بخشنمونه

ممنوعیتعدم تغییر فایل‌های اصلی و عدم پروگرام FPGA

عبارت‌های دقیق و مفید

  • «ابتدا فقط بررسی کن؛ هیچ فایلی را تغییر نده.»
  • «اگر برای ادامه نیاز به تغییر داری، متوقف شو و پیشنهاد تغییر را گزارش کن.»
  • «هیچ نتیجه‌ای را بدون لاگ یا شاهد PASS اعلام نکن.»
  • «موارد تأییدنشده را صریحاً با وضعیت UNKNOWN مشخص کن.»
  • «آزمایش را فقط در مسیر جدید و مستقل انجام بده.»

۷. قالب آماده مأموریت برای Tang Primer 25K

متن زیر را برای هر ممیزی کپی و بخش‌های داخل کروشه را تکمیل کنید:

عنوان: [نام ممیزی]

هدف:
[سؤال فنی مشخصی که باید پاسخ داده شود]

برد و محیط:
Sipeed Tang Primer 25K / GW5A-25A
LiteX در محیط موجود سیستم

محدوده مجاز:
فقط فایل‌ها و مسیرهای مرتبط با این ممیزی را بخوان.
برای هر آزمایش جدید، یک پوشه مستقل زیر
~/litex_work/PRJ/ ایجاد کن.

ممنوعیت‌ها:
- هیچ پروژه قدیمی را تغییر نده.
- به Flash دست نزن.
- FPGA را پروگرام نکن.
- هیچ فایل اصلی یا تنظیمات سراسری را تغییر نده.
- اگر تغییر کد لازم است، ابتدا متوقف شو و طرح تغییر را گزارش کن.

روش:
1) ابتدا ساختار و نسخه فایل‌ها را ثبت کن.
2) فرضیه‌ها و وابستگی‌ها را مشخص کن.
3) تست مستقل و قابل تکرار طراحی کن.
4) فرمان‌ها و خروجی کامل تست را ذخیره کن.
5) نتیجه را با شواهد ارزیابی کن.

قالب گزارش:
- خلاصه نتیجه
- وضعیت GREEN / YELLOW / RED
- فایل‌ها و نسخه‌های بررسی‌شده
- روش و فرمان‌های اجراشده
- تعداد PASS / FAIL / SKIP
- خطاها و محدودیت‌ها
- فایل‌های تولیدشده و مسیرشان
- پیشنهاد گام بعدی

در پایان هیچ تغییری را بدون تأیید من اعمال نکن.
یادآوری مخصوص پروژهمسیر آزمایش‌ها باید زیر ~/litex_work/PRJ/ و مستقل باشد. پروژه‌های قدیمی LiteX دست‌نخورده می‌مانند.

۸. استاندارد گزارش و معیار پذیرش

وضعیتمعناچه زمانی استفاده شود؟
GREENقبول با شواهد کافیهمه معیارهای تعریف‌شده پاس شده و لاگ قابل بازبینی وجود دارد.
YELLOWنتیجه ناقص یا مشروطبرخی تست‌ها انجام نشده، ابهام باقی مانده یا نتیجه فقط شبیه‌سازی است.
REDشکست یا مانع جدیمعیار مهمی شکست خورده یا ریسک حل‌نشده وجود دارد.

گزارش باید تفاوت شبیه‌سازی، سنتز، تحلیل زمان‌بندی و آزمایش روی برد واقعی را حفظ کند. PASS در شبیه‌سازی به معنی تأیید سخت‌افزار واقعی نیست.

۹. قوانین ایمنی و کنترل تغییرات

  • پروژه‌های قدیمی LiteX هرگز تغییر نکنند؛ آزمایش جدید فقط در پوشه مستقل ~/litex_work/PRJ/....
  • هیچ برنامه‌ریزی FPGA، حتی SRAM، بدون اجازه صریح کاربر انجام نشود.
  • Flash تحت هیچ شرایطی بدون مجوز جداگانه لمس نشود.
  • قبل از هر تغییر، فایل هدف، دلیل تغییر، روش بازگشت و اثر احتمالی گزارش شود.
  • هیچ credential، API key، token یا رمز عبوری در GitHub یا گزارش عمومی ثبت نشود.
  • قطعات انتخاب‌شده، سفارش‌داده‌شده، دریافت‌شده، نصب‌شده و آزمایش‌شده وضعیت‌های متفاوت‌اند.
  • درصد پروژه فقط با پیشرفت واقعی و قابل تأیید تغییر کند.
قانون توقفاگر مأموریت مبهم است، به Flash یا پروگرام سخت‌افزار نیاز پیدا می‌کند، یا احتمال تغییر پروژه قدیمی وجود دارد، Hermes باید متوقف شود و قبل از اقدام اجازه بگیرد.

۱۰. عیب‌یابی سریع

فرمان hermes پیدا نمی‌شود

ترمینال جدید باز کنید یا shell را reload کنید. سپس مسیر اجرایی و خروجی hermes --help را بررسی کنید.

اتصال مدل برقرار نمی‌شود

دسترسی شبکه به endpoint، نام مدل، اعتبار کلید، محدودیت نرخ و کد خطای HTTP را بررسی کنید. کلید را در گزارش چاپ نکنید.

پاسخ‌ها کند یا ناقص‌اند

یک مأموریت کوچک‌تر اجرا کنید، خروجی مورد انتظار را محدود کنید و ابتدا بررسی فقط‌خواندنی بخواهید. لاگ زمان و خطا را نگه دارید.

ابزار مورد نیاز در دسترس نیست

با hermes tools وضعیت ابزارها را بررسی کنید. فعال‌سازی ابزار جدید را بدون بررسی مجوزها و ریسک امنیتی انجام ندهید.

گزارش Hermes با نتیجه محلی تفاوت دارد

نسخه فایل، commit، مسیر کاری، محیط مجازی و فرمان دقیق را تطبیق دهید. گزارش را بر اساس شواهد محلی بازتولید کنید.

۱۱. مسیر یادگیری پیشنهادی

  1. مبتدی: اجرای Hermes، بررسی سلامت، گفت‌وگوی ساده و آشنایی با مدل.
  2. کاربردی: نوشتن مأموریت محدود، خواندن فایل‌ها و تهیه گزارش.
  3. فنی: ممیزی کد LiteX، شبیه‌سازی مستقل و تحلیل لاگ‌ها.
  4. پیشرفته: استفاده کنترل‌شده از ابزارها، مهارت‌ها (Skills)، اتصال MCP و خودکارسازی؛ فقط پس از شناخت مجوزها و امنیت.

پیشنهاد می‌شود هر مرحله با یک تمرین کوچک و فقط‌خواندنی تمام شود و قبل از رفتن به مرحله بعد، خروجی آن بازبینی شود.
